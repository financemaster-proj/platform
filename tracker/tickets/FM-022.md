## Context
A rule describing an expense that repeats: rent on the 1st, a subscription on
the 15th. This ticket models and stores rules and exposes CRUD. It deliberately
materialises nothing — FM-023 does that.

Splitting it this way keeps the scheduling problem in one ticket, so a rule
model that turns out to be wrong is found before a scheduler is built on it.

## Acceptance criteria
- [ ] `V5__recurring_rules.sql` creates `recurring_rules`: UUIDv7 pk, `user_id`, `category_id`, `amount`, `currency`, `description`, `frequency`, `day_of_month`, `starts_on`, `ends_on` nullable, `active`, `deleted_at`, timestamps
- [ ] `frequency` is an enum persisted as a **string**, never as an ordinal
- [ ] Supported frequencies decided and documented — monthly only is a legitimate v1
- [ ] `day_of_month` validated 1–31, with the short-month rule decided and documented
- [ ] `ends_on` after `starts_on` enforced by a `CHECK`
- [ ] Full CRUD under `/api/v1/recurring-rules`, user-scoped, 404 for another user
- [ ] A rule referencing another user's category returns 404
- [ ] A rule can be deactivated without being deleted, and the difference is documented
- [ ] `GET /api/v1/recurring-rules/{id}/preview?months=3` returns the dates it *would* generate, computing nothing persistent
- [ ] Occurrence-date calculation is a pure function, unit-tested in `test` with no container
- [ ] Unit tests cover: day 31 in February, day 31 in April, a leap year, a rule ending mid-period

## The short-month rule — decide before writing code

A rule set for day 31 has no 31st in February. The options:

1. **Clamp to the last day of the month.** Day 31 becomes 28 or 29 in February.
   Matches how most subscriptions and rent actually behave.
2. **Skip the month.** February generates nothing. Almost never what a user
   means, and silently loses a rent payment.
3. **Reject day > 28 at creation.** Honest, and annoying for anyone paid on the
   30th.

Clamping is recommended. Whichever is chosen, it is a unit test, not a comment.

## Learning notes
Persist the enum as a string. Stored as an ordinal, inserting a new frequency in
the middle of the Java enum silently reinterprets every existing row — `WEEKLY`
becomes `MONTHLY` across the whole table, with no error and no migration to
blame. It is one annotation to avoid.

The `preview` endpoint is worth more than it looks. It makes the date arithmetic
observable and testable before anything writes rows, so FM-023 starts from a
function already known to be correct. It is also the right UX: a user should see
what a rule will do before it does it.

Keeping occurrence calculation a pure function — in, `LocalDate`s out, no
repository, no clock field — is what lets leap years and short months be tested
in milliseconds. Reach for `java.time.temporal.TemporalAdjusters` rather than
hand-rolling the arithmetic.

`active = false` and `deleted_at` are genuinely different states: paused, versus
gone. If both end up meaning the same thing in every query, one of them is
redundant and should be removed.
