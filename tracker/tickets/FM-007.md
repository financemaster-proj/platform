## Context
The service skeleton: starts, proves it can reach its dependencies, documents
itself. No business logic.

Health was verified on 2026-11-20 and the findings are carried forward below.
What remains is springdoc, graceful shutdown, and making a healthy response say
*which* components were checked.

Package layout follows ADR-0006: package by feature, not by layer.

## Acceptance criteria

- [x] Health endpoint reports DOWN when Postgres is stopped — verified by stopping it
- [x] `GET /actuator/health/readiness` and `/liveness` both exposed

## Observed 2026-11-20 while verifying FM-004

The service was running, so three of this ticket's criteria were re-checked
directly:

| Endpoint | Status |
|---|---|
| `/actuator/health` | 200 `{"groups":["liveness","readiness"],"status":"UP"}` |
| `/actuator/health/readiness` | 200 |
| `/actuator/health/liveness` | 200 |
| `/actuator/info` | **404** |
| `/actuator/env` | 404 |

Two corrections to this ticket:

- **`info` is not exposed.** The criterion says "only `health` and `info`", and
  only `health` is. There is no `management` section in any profile, so this is
  the framework default rather than a decision. Not a security problem — fewer
  endpoints is safer — but either expose `info` deliberately or reword the
  criterion to say `health` alone. Default-deny should be *written down*, because
  a future Boot release changing its defaults is exactly what a committed
  `management.endpoints.web.exposure.include` protects against.
- **`health` does not name its components.** The body reports the probe groups
  and an aggregate `UP`, with no Postgres component, because `show-details` is
  unset. The remaining criterion about naming the component is therefore real
  work, not already done.

Readiness and liveness are both genuinely exposed — Boot 4 enables the probe
groups without configuration here.

## Verified 2026-11-20

With Postgres stopped the endpoint returns **HTTP 503** and `{"status":"DOWN"}`
in ~4ms, on both the first and second call. Two things worth noting that the
criterion did not explicitly ask for:

- It returns 503, not 200-with-a-DOWN-body. Load balancers and Kubernetes read
  the status code, not the JSON, so a 200 here would keep traffic flowing to a
  broken instance.
- It fails in milliseconds rather than blocking on Hikari's 30s connection
  timeout. A health check that blocks is a classic incident: readiness probes
  time out, instances get restarted, and the blocked threads exhaust the
  request pool under load.

The service also recovered on its own when Postgres came back — no restart
needed, Hikari discarded the dead connections and opened new ones.

## Known risk: springdoc on Framework 7

`build.gradle.kts` pins `springdoc-openapi-starter-webmvc-ui:2.8.6` by hand,
because springdoc is not in Spring Initializr and not managed by the Spring Boot
BOM. 2.8.6 targets Spring Framework 6; this service runs Boot 4.1.2 on
Framework 7. That combination is unverified upstream.

If it fails, the options in order: bump to whatever springdoc release targets
Framework 7, or drop springdoc and serve a hand-written OpenAPI document from
`platform/contracts/`. Record which, and why, in this ticket.

## Learning notes
Readiness and liveness are not the same thing, and conflating them causes real
outages. Liveness answers "is this process wedged, restart it"; readiness
answers "can this instance serve traffic right now". A service waiting on a
database is *not ready* but is perfectly *alive* — if liveness checks the
database, one brief database blip restarts every instance you have.

Exposing `/actuator/env` publicly leaks your entire configuration, secrets
included. Default-deny the actuator surface.

Graceful shutdown is what makes a rolling deploy non-disruptive. Without it, SIGTERM
kills in-flight requests and users see errors on every deploy.
