## Context
The first vertical slice through every convention in this project at once:
ADR-0006's package layout, user scoping, soft delete, Problem Details, cursor-free
simple listing, and OpenAPI. Categories are deliberately the simplest aggregate,
so the slice is about the conventions rather than the domain.

Every pattern established here gets copied by expenses, budgets and recurring
rules. Getting it right is worth more than getting it fast.

## Acceptance criteria
- [ ] Package layout per ADR-0006: `category/{domain,application,adapter/in/web,adapter/out/persistence}`
- [ ] `POST /api/v1/categories` creates, returns 201 with a `Location` header
- [ ] `GET /api/v1/categories` lists the caller's categories only
- [ ] `GET /api/v1/categories/{id}` returns one
- [ ] `PATCH /api/v1/categories/{id}` renames
- [ ] `DELETE /api/v1/categories/{id}` **soft**-deletes, returns 204
- [ ] Every query filters by `user_id` — no exceptions
- [ ] Another user's category id returns **404, not 403**, with an integration test proving it
- [ ] A soft-deleted category is absent from list and returns 404 on get
- [ ] A duplicate name returns 409 via the database constraint, not a pre-read check
- [ ] A name that duplicates a *soft-deleted* category succeeds
- [ ] `@Transactional` sits on the application use case, not on the controller or the repository
- [ ] Blank, whitespace-only and over-length names rejected with 400 and per-field violations
- [ ] OpenAPI documents all five operations with request and response examples
- [ ] `user_id` is read from the JWT subject, with a documented stub until sprint 1 exists

## Learning notes
**404 rather than 403 for another user's record** is the whole ticket in one
line. A 403 confirms the record exists, which turns your API into an oracle: an
attacker enumerates ids and learns exactly which ones are real. Return 404 and
they learn nothing. This applies to every user-scoped endpoint you will write.

Soft delete is now costing you a second time. Every read path needs
`deleted_at IS NULL` alongside `user_id`, and forgetting it is the same class of
bug as forgetting user scoping — invisible in testing, serious in production.
Decide **once** where that predicate lives: Hibernate's `@SQLRestriction` on the
entity, or an explicit clause in every repository query. Document the choice.
Scattering it by hand across queries is how one gets missed.

Put `@Transactional` on the use case. On the controller, it holds a database
transaction open while serialising the response. On the repository, every method
is its own transaction and two writes cannot be made atomic.

There is no auth service yet. Stub `user_id` extraction behind a single
interface so sprint 1 replaces one class, not twenty controllers — and make the
stub obviously a stub, so it cannot survive to production quietly.
