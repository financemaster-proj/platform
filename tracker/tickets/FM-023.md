## Context
Turning the rules from FM-022 into real expenses on a schedule. The hardest
ticket in sprint 3, and the only one whose correctness depends on something
other than a request/response cycle.

The roadmap puts "scheduled work without duplicate runs" in sprint 5. Pulling
this forward is a deliberate choice, so the design has to be one that **cannot**
duplicate rather than one that is merely unlikely to.

**The approach: make a double run harmless, not impossible.** A unique
constraint on `(rule_id, occurrence_date)` means the second run's insert is
rejected by the database. Locking and leader election then become a performance
optimisation for sprint 5, not a correctness fix.

## Acceptance criteria
- [ ] `V6__recurring_occurrences.sql` creates `recurring_occurrences`: `rule_id`, `occurrence_date`, `expense_id`, `created_at`
- [ ] **Unique on `(rule_id, occurrence_date)`** — the constraint the whole design rests on
- [ ] A scheduled job materialises due occurrences into real expenses
- [ ] The occurrence row and the expense row are written in the **same transaction**
- [ ] A duplicate insert is caught and treated as "already materialised", not as an error
- [ ] Integration test: running the job twice over the same window creates each expense exactly once
- [ ] Integration test: two *concurrent* job invocations create each expense exactly once
- [ ] Catch-up works — a job that has not run for three months materialises all missed occurrences, in order
- [ ] A rule past its `ends_on` materialises nothing
- [ ] An inactive rule materialises nothing
- [ ] A rule whose category has been soft-deleted is skipped, and that is logged, not silently ignored
- [ ] Materialised expenses are indistinguishable from manual ones to every read endpoint, or carry a flag — decide and document
- [ ] The job is also invocable manually for testing, without waiting for the schedule
- [ ] Each run logs rules examined, occurrences created and occurrences skipped, with the correlation ID from FM-008
- [ ] Budget consumption (FM-021) includes materialised expenses, with a test

## Scope boundary with sprint 5

In scope here: a plain `@Scheduled` job plus the unique constraint. One instance
runs locally, so there is no contention yet, and the constraint makes
correctness independent of that.

**Out of scope, left for sprint 5:** advisory locks or `SELECT ... FOR UPDATE
SKIP LOCKED` so two instances do not both do the *work*; a persisted record of
last-successful-run; backoff and alerting on repeated failure. Write that list
into the ticket when closing it, so sprint 5 inherits a known starting point
rather than a rediscovery.

## Learning notes
"Make duplicates harmless" beats "prevent duplicate runs" and the reason is
worth holding on to: preventing a duplicate run means being certain about
process liveness, clocks and network partitions, and that certainty is not
available. A unique constraint needs no such assumption — it is enforced at the
one place that genuinely serialises, the database. This is the same reasoning
that makes `eventId` the basis for idempotent consumers in sprint 4, and the
same reasoning behind FM-015's idempotency key. Three appearances of one idea.

Catch-up is where naive implementations break. A job written as "what is due
today" silently loses three months of rent after an outage. Written as "what is
due that has not been materialised", the gap fills itself and the outage costs
nothing. The occurrences table is what makes the second phrasing possible.

Logging skips as well as successes is what makes this debuggable. A job that
logs only what it did leaves you unable to answer why February's rent is
missing.

A fixed `@Scheduled(cron = ...)` with no timezone uses the JVM default, which
differs between your laptop and a container. Set it explicitly.
