## Context
Integration tests run against a real Postgres in a container, not H2. H2 has a
different SQL dialect, different transaction semantics and no Postgres-specific
types — tests that pass on H2 and fail on Postgres are worse than no tests.

## Acceptance criteria
- [ ] Testcontainers dependency added to the `integrationTest` source set
- [ ] An abstract base test class starting Postgres once and reused across all integration tests
- [ ] Container reuse enabled so the suite does not pay container startup per class
- [ ] Flyway migrations run against the container before tests
- [ ] One green test: insert a category via the repository, read it back, assert fields
- [ ] One green test asserting `(user_id, name)` uniqueness is enforced **by the database**
- [ ] One green test asserting two different `user_id`s *can* both have "Groceries"
- [ ] `./gradlew integrationTest` passes from clean
- [ ] `./gradlew test` does **not** start any container, and completes in under 5 seconds

## Learning notes
The singleton-container pattern matters: a naive `@Testcontainers` setup starts
a fresh Postgres per test class and a 40-test suite takes ten minutes. Start
one, share it, and roll back or truncate between tests.

Test the unique constraint through the database, not through a service-layer
check. A `findByName` guard before insert is a race condition — two concurrent
requests both see nothing and both insert. The database constraint is the only
real one, and your code needs to handle the resulting exception.

The third test is the one people skip. Asserting that the constraint *does not*
fire across users is what proves you scoped it correctly; the first two pass
just as happily with a wrong `UNIQUE(name)`.
