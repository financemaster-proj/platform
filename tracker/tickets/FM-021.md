## Context
"How much of my March groceries budget have I used" — the question budgets exist
to answer, and the input sprint 4's `BudgetExceeded` event is computed from.

The constraint is the lesson: **one query**, aggregating in the database. Not a
budget fetch, then a page of expenses, then a loop in Java.

## Acceptance criteria
- [ ] `GET /api/v1/budgets/{id}/consumption` returns limit, spent, remaining and a percentage
- [ ] `GET /api/v1/budgets/consumption?month=2026-03` returns the same for every budget that month
- [ ] Aggregation happens in SQL — a single `SUM` grouped by category, not summed in Java
- [ ] The multi-budget endpoint issues a **constant** number of queries regardless of budget count, asserted by a query-count test
- [ ] Soft-deleted expenses are excluded from the sum
- [ ] Expenses in a category with no budget are not silently dropped from the month's picture — decide how they surface
- [ ] A budget with zero matching expenses returns `spent = 0.00`, not null and not absent
- [ ] `spent` and `remaining` use `Money` from FM-012 and serialise as strings
- [ ] `remaining` may be negative when overspent; that is correct and is tested
- [ ] Percentage rounding specified and tested at the boundary — `33.333...%` must be one documented value
- [ ] Integration test: expenses on the first and last day of the month are included, the day before and after are not
- [ ] Only the caller's expenses contribute, proven with two users holding the same category name

## Learning notes
The boundary test is the one that catches real bugs. Month-end inclusivity in a
`BETWEEN` on dates is exactly where off-by-one errors live, and FM-014's choice
of `DATE` over `TIMESTAMPTZ` is what keeps this simple — with a timestamp you
would also be arguing about whether 2026-03-31T23:30 in some timezone is March.

`SUM` over an empty set returns `NULL`, not zero. That `NULL` reaches Java as a
null `BigDecimal` and the first arithmetic on it throws — on the perfectly
ordinary case of a budget nobody has spent against yet. `COALESCE` it in SQL, or
handle it explicitly; either way, there is a test.

The constant-query-count assertion is the same discipline as FM-018, applied
before the bug exists rather than after. A loop calling a per-budget query is
the natural way to write this endpoint, and it is an N+1 wearing different
clothes.

Negative `remaining` being correct rather than clamped to zero is a small
modelling decision with a real consequence: clamping it throws away the
information sprint 4 needs to say *by how much* a budget was exceeded.
