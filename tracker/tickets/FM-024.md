## Context
A production image for expense-service. **Not** for local development — local
iteration stays `./gradlew bootRun` against the compose infra stack (ADR-0002,
FM-003), because rebuilding an image on every code change destroys the feedback
loop.

Deliberately scheduled late. A Dockerfile written before the service has
externalised config (FM-004), a health check (FM-007) and a database connection
(FM-005) has nothing real to containerise, and gets rewritten once they land.

## Acceptance criteria
- [ ] Multi-stage build: a JDK stage to build, a **JRE** stage to run
- [ ] Spring Boot layered jar extracted so dependencies and application code land in separate image layers
- [ ] Changing one source file rebuilds only the application layer — verified by timing two consecutive builds
- [ ] Runs as a **non-root** user
- [ ] `.dockerignore` excludes `build/`, `.gradle/`, `.git/`, `.env`
- [ ] No secret baked into the image — all config via environment at runtime
- [ ] `HEALTHCHECK` wired to the actuator readiness endpoint
- [ ] JVM given container-aware heap settings (`-XX:MaxRAMPercentage`), not a fixed `-Xmx`
- [ ] Final image size recorded in the PR description
- [ ] Image builds in CI and the service starts against the compose stack

## Learning notes
Layer ordering is the whole game. A naive `COPY . .` then build means every code
change invalidates every layer and you push hundreds of megabytes per deploy.
Extract the layered jar so dependencies — which change rarely — sit below
application classes, which change constantly.

Never `-Xmx` in a container. The JVM reads the cgroup memory limit, and a fixed
heap either wastes the limit or gets the process OOM-killed by the kernel when
the limit changes. `MaxRAMPercentage` adapts.

Running as root inside a container is the default and it is wrong: a container
escape then starts from root. It costs two lines to fix.
