## Context
A deliberately two-phase ticket: make the N+1 happen, see it, measure it, then
fix it and prove the fix with a test that fails if it regresses.

The reproduction is not optional padding. An N+1 is invisible in code review and
invisible in a correctness test — it only shows up as query count, which nothing
measures unless you make it.

## Acceptance criteria
- [ ] Phase 1: the list response includes the category *name*, loaded lazily, producing 1 + N queries
- [ ] The query count for a 50-row page is measured and recorded in the ticket
- [ ] Wall-clock time for that page recorded, against a table seeded with at least 10,000 rows
- [ ] Phase 2: fixed with a fetch join or a DTO projection, and the chosen approach justified
- [ ] Query count after the fix recorded alongside the before number
- [ ] A test **asserts the query count** — via Hibernate statistics or a datasource proxy — and fails if it grows
- [ ] The fix does not break FM-017's cursor pagination, proven by re-running its tests
- [ ] If a fetch join was used, confirmed that it does not silently paginate in memory
- [ ] Findings written into `platform/docs/runbooks/` or the ticket, with the before/after numbers
- [ ] `spring.jpa.open-in-view` set explicitly, with the reason recorded

## `spring.jpa.open-in-view` — noted 2026-11-20

It is **on by default** and warns about it on every boot. Left alone during
FM-004 because it is a lazy-loading decision, not a configuration tidy-up, and
it belongs with the ticket that studies lazy loading.

With it on, the persistence context stays open for the whole request, so a
lazily-loaded association resolves during response serialisation — which means
an N+1 can hide in the view layer rather than in the repository, and setting it
to `false` turns that same code into a `LazyInitializationException` instead.
That is the more honest failure: it surfaces at development time rather than as
latency in production.

Set it explicitly either way. Leaving it at the default means the project has
not decided.

## Learning notes
The query-count assertion is the deliverable. Fixing one N+1 is a half-hour;
having a test that catches the next one is what actually matters, because the
next one arrives the moment someone adds a field to a response DTO.

`JOIN FETCH` plus pagination is a trap worth meeting deliberately. Hibernate
cannot apply `LIMIT` to a query that fetch-joins a collection without risking
wrong results, so it fetches **everything** and paginates in memory — and warns
about it in a log line nobody reads. For a to-one association like
expense → category it is safe. For a to-many it is not. Check which you have.

A DTO projection is often the better answer for a list endpoint: select exactly
the columns the response needs, skip entity hydration and the persistence
context entirely. The cost is a second shape to maintain. For a read-heavy list
on a large table, it is usually worth it.

Seed 10,000 rows for the measurement. An N+1 across 5 rows looks fine and
teaches nothing; the point is to see the shape of the problem.
