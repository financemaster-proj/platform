## Context
ADR-0008 is Proposed and blocks every domain ticket below it. A domain model
written before the decision gets rewritten after it.

**The decision taken: pragmatic, in every service.** The JPA entity *is* the
domain object, with behaviour on it. `expense-service` does not get the strict
split originally proposed for it.

This ticket is documentation only — no code. It exists because an undocumented
decision is re-litigated in three months.

## Acceptance criteria
- [ ] ADR-0008 status changed from Proposed to **Accepted**, dated
- [ ] The decision stated as pragmatic for all services, superseding the per-service split it proposed
- [ ] The consequences section rewritten to describe what was actually accepted, not the strict option
- [ ] The guardrails below written into the ADR as the cost of this choice

- [ ] The open decision removed from `platform/CLAUDE.md`

## Guardrails that come with pragmatic

Choosing pragmatic is choosing to accept persistence leakage. These keep it from
becoming a tutorial-shaped CRUD app anyway:

- Behaviour lives **on** the entity. An entity with only getters and setters,
  plus a service class holding the rules, is the layered anti-pattern wearing a
  different package name.
- No setters for anything with an invariant. Expose intention-named methods
  (`recategorise`, `softDelete`) rather than `setCategory`, `setDeletedAt`.
- `Money` is still a value object — an `@Embeddable` with behaviour, never two
  loose columns handled by the service layer. FM-012.
- JPA's no-arg constructor stays `protected`, not `public`.
- The package layout from ADR-0006 still holds. Pragmatic removes the second
  model, not the feature packaging.

## Learning notes
The thing being given up is worth naming precisely, because you may want it
later in `investment-service`: a pure domain model can be unit-tested with no
Spring context and no database, which is what makes domain tests run in
milliseconds. With the entity as the domain object, any test touching
persistence behaviour — lazy loading, dirty checking, cascade — needs a real
database and lands in `integrationTest`.

Watch for that pressure as budgets and recurring rules grow. If domain logic
starts needing a container to test, that is the evidence that would justify
revisiting this for `investment-service`, and ADR-0008 already leaves that open.
