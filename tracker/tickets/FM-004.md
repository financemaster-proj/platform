## Context
No secret is ever committed. Local development reads a gitignored `.env`; a
committed `.env.example` documents every variable the service needs, so a fresh
clone is runnable without guesswork.

This comes first in sprint 0 because `application.yaml` already references
`${DB_URL}`, `${DB_USERNAME}` and `${DB_PASSWORD}` with nothing defining them
and no profile split. Every ticket below needs a service that starts.

Note FM-003: a native Postgres holds `127.0.0.1:5432` on this machine, so the
compose container is mapped to **15432**. That port must not be hardcoded in a
committed file.

**Amended 2026-11-20:** the implementation embeds the port in a single `DB_URL`
rather than splitting out `DB_PORT`. Accepted — one variable instead of three,
and the URL format is self-documenting in `.env.example`. Revisit only if a
component ever needs the host or port separately.

## Reviewed 2026-11-20 — 3 of 9 criteria pass

`.gitignore` is correct (`.env` at line 40, plus `.env.local`, `*.pem`, `*.key`),
no committed yaml holds a secret, and `show-sql` differs correctly between
profiles. Five findings against the rest.

### 1. Nothing loads `.env` — the blocking one

Spring Boot has **no native `.env` support**, and nothing in `build.gradle.kts`
adds it. Verified by running `./gradlew bootRun` with no exported `DB_*`:

```
Driver org.postgresql.Driver claims to not accept jdbcUrl, ${DB_URL}
```

The placeholder was never resolved — the literal string `${DB_URL}` reached the
JDBC driver. Flyway's auto-configuration pulled the property through a path that
does not raise `Could not resolve placeholder`, so there is no guardrail here at
all. Criterion 9 cannot pass until this is fixed.

Options: source `.env` into the shell before `bootRun` (zero dependencies,
easily forgotten); add `me.paulschwarz:spring-dotenv` (one dependency, identical
behaviour in `bootRun`, the IDE and tests); or have Gradle inject `.env` into the
`bootRun` task environment (no runtime dependency, no help for IDE or tests).
The middle option is what makes "fresh clone plus `cp .env.example .env`" true.

### 2. `application-local.yaml` never loads

No active profile is set in any yaml or in `build.gradle.kts`, and the boot log
shows no active-profile line. Separately, `application.yaml` and
`application-local.yaml` are **byte-for-byte identical** — `diff` is empty. The
two faults mask each other: the service behaves as though `local` loaded,
because the file that did load is a copy.

Profile files **merge onto** the base rather than replacing it, so the base
should hold only what is common and each profile only its differences. Today the
port is specified in three places.

Prefer `spring.profiles.default: local` over `spring.profiles.active`. A
committed `active` means production must *override* it, and one missing env var
boots prod with `show-sql: true`. `default` applies only when nothing else is
set, so `bootRun` gets local and `SPRING_PROFILES_ACTIVE=prod` works untouched.

### 3. `.env.example` cannot be used

Three bare keys, no values, no comments, no trailing newline. Copied to `.env`
it produces exactly the failure in finding 1. It needs a dummy value shaped like
the real one, a comment per variable, and FM-003's **15432** port — which is the
most surprising thing about this setup and is currently recorded nowhere a fresh
clone would look.

### 4. Fail-fast not started

No `@ConfigurationProperties` class exists, so criteria 6 and 7 are untouched.
The failure observed is the kind the criterion exists to rule out: 1.3s into
startup, inside `entityManagerFactory` creation, with a driver-level message. A
`@Validated @ConfigurationProperties` with `@NotBlank` fails during environment
binding, before Flyway or Hikari are constructed, and names the property.

### 5. Minor

- `application-prod.yml` uses `.yml` while the others use `.yaml`. Spring loads
  both, but a `grep` for `application*.yaml` silently skips prod. Pick one.
- The `springdoc` dependency added to `build.gradle.kts` is FM-007's work, and
  its comment cites FM-004 — true before the renumbering, stale now.

## Implemented 2026-11-20 — branch `feature/FM-004-externalised-config`

Uncommitted in the working tree. Eight of nine criteria met; criterion 6 was
amended, and the reason is the most interesting thing in this ticket.

### `.env` is now read, with no dependency and no shell step

```yaml
spring:
  config:
    import: optional:file:.env[.properties]
```

Spring Boot parses `.env` as a properties file natively. `optional:` means a
deployed container that supplies real environment variables starts fine without
one, and real environment variables outrank the file — so the same
configuration works locally and in production. No `spring-dotenv`, no
`set -a; source .env`.

The cost, documented in `.env.example`: it is properties syntax, not shell. Do
not quote values, and escape a backslash as `\\`.

### `spring.profiles.default`, not `active`

Verified: `No active profile set, falling back to 1 default profile: "local"`.
A committed `spring.profiles.active: local` would have to be *overridden* in
production, so one missing variable would boot prod with local settings.
`default` applies only when nothing else sets a profile.

`application.yaml` was also reduced to what is genuinely common. It and
`application-local.yaml` had been byte-identical; the profile files now hold
only their differences, and `application-prod.yml` was renamed to `.yaml`.

### Fail-fast needed an `EnvironmentPostProcessor`, not `@ConfigurationProperties`

Criterion 6 asked for `@Validated @ConfigurationProperties`. It was built that
way first, and **it does not work.** `DataSourceAutoConfiguration` fails before
any `@ConfigurationProperties` bean of ours is created, so the message was:

```
Failed to configure a DataSource: 'url' attribute is not specified
Reason: Failed to determine suitable jdbc url
Action: ... you may need to activate it (no profiles are currently active)
```

It names neither `DB_URL` nor the file the value should come from, and the
suggested action is actively misleading — `local` *was* the default profile.

`RequiredConfigurationPostProcessor` runs during environment preparation,
before any bean exists, which is the only point early enough. With a
`FailureAnalyzer` to render it, a missing variable now produces:

```
Description:

The following required configuration variables are not set:

    - DB_URL
    - DB_USERNAME
    - DB_PASSWORD

Action:

Copy the example file and fill in the values:

    cp .env.example .env
```

All three reported together, not one per restart. A single missing variable
reports just that one — verified separately.

### Two mechanism details worth keeping

- **`EnvironmentPostProcessor` is registered in `META-INF/spring.factories`,
  not in a `.imports` file.** It was written as `.imports` first and silently
  did nothing: the application started, the check never ran, and the only
  symptom was the old DataSource error. `.imports` is the auto-configuration
  mechanism; these run earlier than that, hence
  `SpringFactoriesEnvironmentPostProcessorsFactory`. A registration that fails
  silently is worth meeting once.
- **`org.springframework.boot.env.EnvironmentPostProcessor` is deprecated for
  removal in Boot 4.** The replacement is
  `org.springframework.boot.EnvironmentPostProcessor` — same method, different
  package. Compiling with warnings visible is what caught it.

### Integration tests had to be made CI-safe

The check would have failed `integrationTest` on CI, where there is no `.env`
and Testcontainers supplies the datasource through `@ServiceConnection`. The
post-processor skips the `test` profile, and `ExpenseServiceApplicationTests` now
declares `@ActiveProfiles("test")`.

Verified by running `integrationTest` with the `.env` import disabled — green,
which is what CI will do. This belongs to FM-004 rather than FM-006 because
FM-004 introduced the failure mode.

## Learning notes
Fail-fast on missing config is worth the effort. The alternative boots happily
and throws on the first request that touches the missing value, which is much
harder to diagnose — and in a four-service system it will be the *other* team's
service that looks broken.

`@ConfigurationProperties` with `@Validated` gives startup validation and a
typed object. `@Value` gives stringly-typed config checked at first use.

`.env.example` is real documentation. If it drifts from reality, a future you on
a new laptop loses an hour.
