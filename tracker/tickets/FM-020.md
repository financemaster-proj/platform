## Context
A budget is a limit on spending in one category for one calendar month. It is
the first aggregate in this service with a genuine invariant of its own, which
makes it the first place the pragmatic-entity decision (FM-011) is really
tested: the rules belong **on** the entity.

Note the boundary: budgets live here because `BudgetExceeded` is this service's
event to emit in sprint 4. Spending *reports* belong to analytics-service and
are not in scope.

## Acceptance criteria
- [ ] `V4__budgets.sql` creates `budgets`: UUIDv7 pk, `user_id`, `category_id`, `period_month` DATE, `limit_amount` NUMERIC(19,2), `currency`, `deleted_at`, timestamps
- [ ] `period_month` stored as the first day of the month, with a `CHECK` enforcing it
- [ ] Partial unique index on `(user_id, category_id, period_month) WHERE deleted_at IS NULL`
- [ ] `POST /api/v1/budgets` creates one; `PUT` on the same period updates the limit
- [ ] `GET /api/v1/budgets?month=2026-03` lists the caller's budgets for a month
- [ ] `DELETE` soft-deletes
- [ ] A zero or negative limit is rejected with 400
- [ ] A budget for a category belonging to another user returns 404
- [ ] A duplicate budget for the same category and month returns 409
- [ ] Behaviour lives on the entity — a method that answers "is this amount within the limit", not a service that reads `getLimitAmount()` and compares
- [ ] A budget may be set for a past month, or may not — decide, document, test
- [ ] OpenAPI documents the month parameter format

## Learning notes
Representing a month as a `DATE` pinned to the first of the month, with a
`CHECK` constraint, is the cheap version of a period type. The alternative —
separate `year` and `month` integer columns — makes every range query arithmetic
and cannot use a normal date index. The `CHECK` is what stops a stray
`2026-03-17` from creating a second, invisible "March" budget.

This is where the pragmatic model earns or loses the argument. If `Budget` ends
up as a bag of getters with the comparison logic in `BudgetService`, you have
the layered design with extra steps, and FM-011's guardrails exist precisely to
prevent that. Put `exceededBy(Money spent)` on the entity and the next
aggregate follows the same shape.

Deciding whether past-month budgets are allowed is a product question with a
technical consequence: allowing them means budget evaluation can never assume
"the current month", and sprint 4's `BudgetExceeded` has to be computed per
period rather than for today. Cheaper to decide now than to discover in sprint 4.
