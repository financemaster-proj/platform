## Context
In a four-service system, "which log lines belong to this one request" is
unanswerable without a correlation ID threaded through everything. Set the
pattern up now, in the first service, so the other four copy something that
already works. Retrofitting this across five services in sprint 7 is miserable.

## Acceptance criteria
- [ ] Logs emitted as single-line JSON in the `prod` profile; human-readable in `local`
- [ ] Every log line carries `timestamp`, `level`, `logger`, `message`, `service`, `traceId`
- [ ] A servlet filter reads `X-Correlation-Id` from the request, or generates a UUIDv7 if absent
- [ ] The correlation ID is placed in MDC and appears on every log line for that request
- [ ] The correlation ID is echoed back on the response in `X-Correlation-Id`
- [ ] MDC is cleared in a `finally` block
- [ ] No secrets, tokens, passwords or full request bodies are ever logged — grep the codebase to confirm
- [ ] Convention documented in `platform/docs/runbooks/logging.md`

## Learning notes
Clearing MDC in `finally` is not optional. Servlet threads are pooled and reused;
leak a correlation ID and the next unrelated request logs under the previous
request's identity, which is the kind of bug that makes an incident unreadable.

Decide the field names now and write them down. Inconsistent field names across
services make log aggregation useless later — `userId` in one service and
`user_id` in another means two queries where there should be one.
