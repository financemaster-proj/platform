## Context
Five services will each need near-identical build files. Establish the shape once
on `auth-service`, then copy it. Polyrepo means no shared build logic across
repos, so the convention lives in `platform/docs/runbooks/new-service.md` as a
documented recipe rather than as inherited code.

## Acceptance criteria
- [x] Gradle wrapper committed (`gradlew`, `gradlew.bat`, `gradle/wrapper/`)
- [x] Java toolchain pinned to 21 via `java.toolchain.languageVersion`
- [x] Spring Boot and dependency-management plugin versions pinned explicitly, not floating
- [x] `./gradlew build` succeeds from a clean clone with no local Gradle install
- [x] Separate `test` and `integrationTest` source sets, with distinct Gradle tasks
- [x] `integrationTest` is **not** wired into `check` — `./gradlew build` starts no container
- [x] Verified: `docker ps` stays empty for the whole of `./gradlew build`
- [x] The recipe written up in `platform/docs/runbooks/new-service.md`

## Decision: integrationTest is not part of `check`

`./gradlew build` runs unit tests only and needs no Docker, so it stays fast
enough to run constantly.

**The consequence, stated plainly:** nothing runs the integration tests
automatically. If CI only calls `./gradlew build`, the suite goes green while
every integration test sits unexecuted — a pipeline that tests nothing is worse
than no pipeline, because it is trusted.

FM-010 therefore calls `./gradlew integrationTest` as its own explicit step.
That step is load-bearing, not redundant. Do not remove it to speed up CI.

## Learning notes
Pin the toolchain rather than relying on `JAVA_HOME`: it is what makes the build
reproducible on CI and on a future machine. Keep unit and integration tests in
separate source sets from day one — you want `./gradlew test` to stay fast
enough to run on every save, which it cannot be if it boots containers.
