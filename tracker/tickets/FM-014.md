## Context
The schema the rest of sprint 3 is built on. Two tables: `expenses`, and the
table that makes `Idempotency-Key` work in FM-015.

One modelling decision is worth more than the rest of the migration: **an
expense happens on a date, not at an instant.**

## Acceptance criteria
- [ ] `V2__expenses.sql` creates `expenses`: UUIDv7 pk, `user_id` UUID (no FK), `category_id` FK to `categories`, `amount` NUMERIC(19,2), `currency` CHAR(3), `spent_on` DATE, `description`, `deleted_at`, `created_at`, `updated_at`
- [ ] `spent_on` is `DATE`, not `TIMESTAMPTZ`; `created_at` and `updated_at` are `TIMESTAMPTZ`
- [ ] `amount` is `NUMERIC(19,2)` — never `float8`, `money` or `double precision`
- [ ] `currency` is `NOT NULL` with a `CHECK` constraint restricting it to `INR`
- [ ] `amount >= 0` enforced by a `CHECK` constraint, matching FM-012's rule
- [ ] `category_id` FK is `ON DELETE RESTRICT`, with the soft-delete interaction documented in the ticket
- [ ] `V3__idempotency.sql` creates `idempotency_keys`: key, `user_id`, endpoint, request fingerprint, response status, response body, `created_at`
- [ ] Unique on `(user_id, key)` — a key is scoped to its user, never global
- [ ] Both migrations run on a clean database and `ddl-auto=validate` passes against the entities
- [ ] Deliberately mismatch one field and confirm boot fails

## The FK and soft delete interact badly — decide and write it down

`ON DELETE RESTRICT` plus soft delete means a *soft-deleted* expense still holds
a real FK row, so deleting its category is still blocked. The user sees "this
category is in use" referring to an expense they deleted.

Pick one and record it here:

1. Category delete checks only non-deleted expenses, and soft-deletes the
   category regardless. Simple; leaves soft-deleted expenses pointing at a
   soft-deleted category, which is consistent if reads filter both.
2. Category delete is blocked by any expense, deleted or not, with the message
   saying so. Honest, mildly annoying.
3. Hard-purge soft-deleted expenses after a retention window, so the problem
   expires. Needs a retention policy, which is a decision you do not have yet.

Option 1 is the cheapest and does not need a policy you have not written.

## Learning notes
`DATE` for `spent_on` is the decision to argue about, so argue it now: a
timestamp forces a timezone on something that does not have one. "I bought
coffee on the 14th" is true in the user's life regardless of UTC offset. Store
it as an instant and you invent a question — whose midnight? — that then
silently decides which month a late-evening expense lands in, which changes
budget totals. Audit timestamps (`created_at`) are genuinely instants and stay
`TIMESTAMPTZ`. The two are different kinds of time.

`NUMERIC(19,2)` and never Postgres's `money` type: `money` carries a
server-locale-dependent currency and cannot be changed per row, which is wrong
the moment a second currency appears.

Storing the response body in `idempotency_keys` is what makes a retry return the
*original* result instead of a fresh 201 with a new id. The request fingerprint
is what detects the dangerous case: the same key sent with a different body,
which is a client bug and must be a 422, not a silent replay.
