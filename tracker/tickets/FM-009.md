## Context
Every API in this system returns errors in one documented shape. Spring Boot
supports RFC 9457 Problem Details natively, so there is no reason to invent a
custom error envelope.

Do this before any real endpoint exists. Retrofitting error handling means
revisiting every controller.

## Acceptance criteria
- [ ] A `@RestControllerAdvice` producing `application/problem+json` for all handled errors
- [ ] Bean validation failures return 400 with per-field violations in an `errors` extension
- [ ] Unknown resource returns 404 with a meaningful `detail`
- [ ] A database constraint violation maps to 409, not 500
- [ ] Unhandled exceptions return a generic 500 leaking **no** stack trace, class name or SQL
- [ ] The 500 response includes the correlation ID so a user can quote it in a report
- [ ] The full stack trace **is** logged server-side at ERROR with that correlation ID
- [ ] An integration test asserting a 500 body contains no package names and no SQL fragments
- [ ] The error shape documented in `platform/docs/architecture/overview.md` or a runbook

## Learning notes
The asymmetry is the lesson: maximum detail in the logs, minimum detail in the
response. A stack trace in an HTTP body tells an attacker your framework
versions, your package structure and sometimes your SQL. The correlation ID
bridges the gap — the user reports an opaque id, you find everything.

Mapping constraint violations to 409 matters once FM-005's partial unique index
exists: a duplicate category name is a client error the client can fix, not a
server fault. A 500 there sends the user away with nothing actionable.

Write the test that asserts the *absence* of information. It is the only way to
stop a well-meaning future change from putting `ex.getMessage()` back in the
response body.
