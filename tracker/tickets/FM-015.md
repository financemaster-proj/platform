## Context
The core write path of the service, and the one place where a retry must not
create a second financial record.

Per the API conventions in `platform/docs/architecture/overview.md`,
`Idempotency-Key` is **required** on any POST creating a financial record. This
is where that convention gets implemented, and the implementation gets reused by
investment-service in sprint 5.

## Acceptance criteria
- [ ] `POST /api/v1/expenses` creates an expense, 201 with a `Location` header
- [ ] Request body uses `Money` from FM-012 — amount as a string, currency explicit
- [ ] `Idempotency-Key` header is **required**; absent means 400, not a silent create
- [ ] The same key replayed returns the **original** response body and status, and creates nothing
- [ ] The same key with a *different* request body returns 422
- [ ] Keys are scoped per user: two users may use the same key value independently
- [ ] The key is persisted in the **same transaction** as the expense
- [ ] Integration test: two concurrent requests with one key produce exactly one expense
- [ ] `category_id` belonging to another user returns 404, not 403
- [ ] A soft-deleted category cannot be assigned to a new expense
- [ ] `spent_on` in the future rejected with 400; a documented cutoff for how far back is allowed
- [ ] `UUIDv7` used for the id, not `UUIDv4`, with the reason recorded
- [ ] OpenAPI documents the header, the 422, and a replay example

## Learning notes
The transaction boundary is the entire point. If the expense commits and the key
write fails, a retry creates a duplicate — the exact bug the header exists to
prevent. If the key commits and the expense fails, the user can never submit
that request at all. One transaction, both rows, or neither.

The concurrency test is the one that finds the real bug. A sequential replay
test passes against a naive read-then-write implementation; two simultaneous
requests do not. The fix is the unique constraint on `(user_id, key)` doing the
work — insert the key first, let the database reject the second, and treat that
rejection as "this is a replay" rather than as an error.

The 422 for a mismatched body is not pedantry. A client that reuses a key for a
different payload has a bug, and silently replaying the old response hides it —
the user sees a success for a request that never happened. Fail loudly.

UUIDv7 is time-ordered, which keeps B-tree inserts at the right-hand edge of the
index instead of scattering them across every page. UUIDv4 on a large table
turns every insert into a random page write. Both are non-enumerable, which is
the security property; only v7 has the locality property.
