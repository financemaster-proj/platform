## Context
FM-017's list query is the hottest read in the service. This ticket is about
proving it uses an index, with `EXPLAIN ANALYZE` output pasted into the ticket
rather than an assumption that it probably does.

Small ticket, disproportionate payoff — and it is the first time in this project
that a decision is made from a measurement.

## Acceptance criteria
- [ ] Table seeded with at least 100,000 expenses across several users
- [ ] `EXPLAIN (ANALYZE, BUFFERS)` captured for the list query **before** any index is added
- [ ] A composite index added matching the query: `(user_id, spent_on DESC, id DESC)`
- [ ] Partial on `WHERE deleted_at IS NULL`, and whether that helped recorded either way
- [ ] `EXPLAIN (ANALYZE, BUFFERS)` captured after, showing an index scan rather than a sequential scan
- [ ] Before and after plans, and timings, pasted into this ticket
- [ ] The index is added by a Flyway migration, not by hand
- [ ] Column order in the index justified in one or two sentences
- [ ] A deep page — cursor far into the result set — measured, showing it has not degraded
- [ ] Any index that turns out not to be used is **removed**, and that noted

## Learning notes
Column order in a composite index is not arbitrary and the rule is worth
internalising: equality predicates first, then the range or sort columns.
`user_id` is always an equality filter, so it leads; `spent_on` and `id` follow
in the sort's own direction so Postgres can walk the index and skip sorting
entirely. Reverse them and the index cannot serve the filter.

An index whose direction matches the `ORDER BY` lets the plan drop the sort node
altogether. Seeing that node disappear between the two plans is the clearest
feedback loop in database work.

Deep pages are where offset pagination dies and cursor pagination does not —
`OFFSET 50000` makes Postgres read and discard fifty thousand rows, while a
cursor seeks straight to the key. Measuring both is how that stops being
something you were told and starts being something you know.

Removing an unused index matters too. Every index slows writes and takes space;
one that no plan chooses is pure cost. Checking `pg_stat_user_indexes` later is
how you find the ones that stopped being used.
