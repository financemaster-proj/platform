## Context
The read path that everything else in the product hangs off, and the one that
has to still work when the table has a hundred thousand rows.

Cursor pagination, per the API conventions — not offset. Offset drifts under
concurrent inserts and degrades at depth.

## Acceptance criteria
- [ ] `GET /api/v1/expenses` returns a page plus a `nextCursor`, absent on the last page
- [ ] Sort is `(spent_on DESC, id DESC)` — a deterministic total order, never `spent_on` alone
- [ ] The cursor is opaque: base64 of the sort-key tuple, not a raw offset or a row number
- [ ] A tampered or malformed cursor returns 400, not a 500 and not silently page one
- [ ] `limit` has a default and a hard maximum; a larger request is clamped or rejected, documented either way
- [ ] Filters: `from`/`to` on `spent_on`, `categoryId`, and free-text on description
- [ ] Filters compose, and the cursor remains correct when filters are applied
- [ ] Soft-deleted expenses never appear
- [ ] Only the caller's expenses appear, with a test seeding two users
- [ ] Integration test: insert a new expense between fetching page 1 and page 2, and assert no row is skipped or duplicated
- [ ] The equivalent offset test is written too, demonstrating the drift that cursoring avoids
- [ ] OpenAPI documents the cursor as opaque, with the stability guarantee stated

## Learning notes
The tie-breaker in the sort key is not optional. Order by `spent_on DESC` alone
and every expense on the same date is in an unspecified order, so a cursor
pointing "after 2026-03-14" cannot know which of that day's six expenses were
already sent. Adding `id DESC` makes the order total, which is what makes the
cursor well-defined. This is the single most common cursor-pagination bug.

Write the offset-drift test even though you are not shipping offset. Watching a
row get skipped because a newer row shifted the window is what makes the reason
for cursoring concrete, and it takes ten minutes. Keep it as documentation.

Keep the cursor opaque — base64, and ideally signed. Expose the sort tuple as a
readable query parameter and clients will start constructing them by hand, and
then your sort key can never change without breaking them.

The filtered-cursor case is where this gets genuinely tricky: the cursor encodes
a position in a *filtered, ordered* result set, so a client that changes the
filter and keeps the cursor is asking a meaningless question. Decide whether to
detect that or document it.
