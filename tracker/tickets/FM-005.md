## Context
Every schema change in this project goes through Flyway. Hibernate's `ddl-auto`
stays `validate` permanently — never `update`, never `create`.

The baseline creates `categories`, the simplest real table in this domain and
the one expenses will reference.

Because this project uses **soft delete**, the uniqueness rule is not the
obvious one. See the criteria.

## Acceptance criteria
- [ ] Flyway migrations live in `src/main/resources/db/migration`
- [ ] `V1__baseline.sql` creates `categories`: UUID pk, `user_id` UUID (no FK), `name`, `deleted_at`, `created_at`, `updated_at`
- [ ] Uniqueness is a **partial** unique index: `UNIQUE (user_id, name) WHERE deleted_at IS NULL`
- [ ] Verified: soft-delete a category, then successfully create a new one with the same name
- [ ] `spring.jpa.hibernate.ddl-auto=validate` in every profile
- [ ] Migration runs automatically on boot against a clean database
- [ ] Deliberately mismatch an entity field and confirm boot **fails** with a validation error
- [ ] Flyway naming convention documented in `platform/docs/runbooks/migrations.md`

## Learning notes
The unique constraint is on `(user_id, name)`, never `name` alone. Two users
must both be able to have a "Groceries" category. Getting this wrong is the most
common multi-tenancy bug and it is invisible until you have a second user —
exactly when it is most expensive to fix.

**The partial index is the subtle half.** A plain `UNIQUE (user_id, name)`
combined with soft delete means deleting "Groceries" permanently reserves the
name: the row is still there, the constraint still sees it, and the user gets a
409 on a category they believe they deleted. Scoping the index to
`WHERE deleted_at IS NULL` is the fix, and it is the first of several places
where soft delete costs something. Write that cost down as you meet it.

`user_id` has **no foreign key**. The users table lives in another service's
database and a cross-database FK cannot exist. This feels wrong the first time;
it is correct here (ADR-0004).

The deliberate-mismatch step is the most valuable part of this ticket.
`validate` turns schema drift into a loud startup failure instead of a silent
runtime bug at 3am. Make it fail once so you know what the failure looks like.

Never edit an applied migration — Flyway checksums them and will refuse to
start. Fixing a bad migration means writing a new one forward.
