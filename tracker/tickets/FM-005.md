## Context
Every schema change in this project goes through Flyway. Hibernate's
`ddl-auto` is set to `validate` permanently — never `update`, never `create`.

## Acceptance criteria
- [ ] Flyway on the classpath, migrations in `src/main/resources/db/migration`
- [ ] `V1__baseline.sql` creates the `users` table: UUID pk, email (unique, citext or lower-cased unique index), password_hash, created_at, updated_at
- [ ] `spring.jpa.hibernate.ddl-auto=validate` in every profile
- [ ] Migration runs automatically on boot against a clean database
- [ ] Deliberately mismatch an entity field and confirm boot *fails* with a validation error
- [ ] Flyway naming convention documented in `platform/docs/runbooks/migrations.md`

## Learning notes
The deliberate-mismatch step is the most valuable part of this ticket. `validate`
turns schema drift into a loud startup failure instead of a silent runtime bug at
3am. Make it fail once so you know what the failure looks like.

Never edit an applied migration — Flyway checksums them and will refuse to start.
Fixing a bad migration means writing a new one forward. This feels annoying now
and will save you from destroying production data later.
