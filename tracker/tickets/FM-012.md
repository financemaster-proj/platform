## Context
Every amount in this service is money, and money is the one type this project
refuses to get wrong. One `Money` type, used everywhere, with the rules encoded
in it rather than remembered by each caller.

**Scope decision: single currency.** Only INR is accepted. Currency is still
explicit in the column, in the Java type and in the JSON — so adding a second
currency later is a migration and a validation change, not a redesign. There is
no FX rate anywhere in this service.

## Acceptance criteria
- [ ] `Money` is an `@Embeddable` holding `BigDecimal amount` and a currency, both non-null
- [ ] Scale is explicitly 2, set on construction — never inherited from whatever the caller passed
- [ ] `double` and `float` appear nowhere in the service — verified by grep
- [ ] A non-INR currency is rejected at the web boundary with a 400 Problem Details response
- [ ] `plus` / `minus` throw if currencies differ, even though only one is currently allowed
- [ ] Negative amounts rejected at construction, with a documented reason
- [ ] Serialises as `{"amount": "1234.50", "currency": "INR"}` — amount a **string**
- [ ] Deserialises a JSON *number* either by rejecting it or by parsing it losslessly; whichever, there is a test
- [ ] Unit test: rounding at the scale boundary behaves as specified, asserted on exact values
- [ ] Unit test: `0.1 + 0.2` equals exactly `0.30`
- [ ] All of the above tested in `test`, not `integrationTest` — no container needed

## Learning notes
Money as a JSON number is the one that bites hardest. Most parsers decode JSON
numbers as IEEE 754 doubles, which cannot represent `0.1` exactly. Keep money as
a string on the wire and `BigDecimal` in Java, with explicit scale and explicit
currency.

Explicit scale is separate from `BigDecimal`. `new BigDecimal("10.5")` has scale
1, `new BigDecimal("10.50")` has scale 2, and they are **not** `equals()` even
though `compareTo` says they are equal. If scale is set on construction, that
asymmetry never reaches your code. If it is not, you will eventually write
`assertEquals` on two amounts that are the same number and watch it fail.

Keeping currency explicit while allowing only one value looks like pointless
ceremony today. It is the difference between a future second currency being a
migration, and being a rewrite of every arithmetic site in the service.

Rejecting negative amounts is a real modelling choice, not an obvious one: a
refund is arguably a negative expense. Decide, write the reason in the ADR or
the ticket, and be consistent. If refunds get their own type later, that is a
better answer than an expense that is sometimes negative.
