# 0007 — Docs-as-code and a file-based tracker

- **Status:** Accepted
- **Date:** 2026-11-18

## Context
Confluence and Jira were the original choice, and free sites were created. The
Atlassian OAuth connector proved to be scoped to the wrong account and granted
no Confluence permissions, making it unusable without repeated re-authorisation.

Alternatives considered: GitHub Issues with an organisation-level Project board;
Notion; Linear; plain markdown.

A requirement that narrowed it sharply: both a human and an agent need read and
write access to tickets and docs. Every hosted option puts an OAuth grant on
that path. The filesystem does not.

## Decision
- **Documentation** — markdown under `platform/docs/`, reviewed in pull requests
  alongside the code it describes. Diagrams in Mermaid, which GitHub renders natively.
- **Tracker** — one markdown file per ticket under `platform/tracker/tickets/`,
  with YAML frontmatter for structured fields. `BOARD.md` is generated by
  `tracker/board.py`, which also validates the frontmatter.

## Consequences

**Benefits**
- A doc and the code it describes change in the same reviewed diff, so docs
  cannot silently rot the way a wiki does.
- Tickets are versioned, diffable, greppable and work offline.
- No authentication on the path between either collaborator and the tracker.
- One file per ticket means ticket-level git history and no edit conflicts.

**Accepted costs**
- No burndown or velocity charts. Sprint metrics are computed by `board.py` or by hand.
- No board UI, no drag-and-drop, no notifications.
- `BOARD.md` is stale until regenerated — a discipline, not a guarantee.
- No Jira experience gained, which is a line on job descriptions. The concepts
  transfer; the UI takes a day to learn when needed.

## Reversibility
Frontmatter is structured data. A script could import every ticket into GitHub
Issues, Jira or Linear later with no information loss.
